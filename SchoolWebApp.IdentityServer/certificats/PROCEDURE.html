Certificats de signature des jetons

Mimia — serveur d'identité. Procédure complète : générer, transférer, renseigner, vérifier.

1. De quoi il s'agit

Le serveur d'identité délivre des jetons aux parents qui se connectent. Pour reconnaître ceux qu'il a lui-même émis, il les signe avec une clé. Ces deux fichiers contiennent cette clé : l'un sert à signer les jetons, l'autre à les chiffrer.

Ce n'est PAS le certificat HTTPS du site. Rien à voir avec le cadenas du navigateur, ni avec Let's Encrypt, ni avec quoi que ce soit qui s'achète. Personne d'extérieur ne valide ces certificats : le serveur signe, et c'est le même serveur qui vérifie. Un certificat auto-signé est donc parfaitement correct ici — c'est même la pratique normale.

Pourquoi il faut les poser

Sans eux, le serveur en fabrique un au démarrage et le range dans le dossier personnel du conteneur — un espace qui disparaît à chaque reconstruction d'image. La clé change, et tous les jetons déjà émis deviennent invalides d'un coup.

Conséquence concrète : à chaque déploiement d'une nouvelle version, tous les parents connectés sont déconnectés et doivent ressaisir leur mot de passe. Rien n'est perdu — ni données, ni abonnement — et les enfants connectés par code ne sont pas touchés, leurs sessions ne passent pas par ce mécanisme. Mais c'est une gêne qui revient à chaque mise à jour.

2. Ce qu'il faut avant de commencer

OutilOù
openssl Fourni avec Git pour Windows. Ouvrez « Git Bash » et tapez openssl version : si un numéro s'affiche, c'est bon.
Un mot de passe Il est déjà écrit dans la configuration. Voir juste en dessous où le trouver — il ne s'invente pas, il se recopie.

Où lire le mot de passe

Attention : deux fichiers portent ce nom, un par projet. Celui de l'API ne contient pas ce bloc — c'est normal, ce n'est pas lui qui signe les jetons. Prenez celui du serveur d'identité : 

SchoolWebApp.IdentityServer/appsettings.Production.json
        ↑ celui-ci

SchoolWebApp/appsettings.Production.json
        ↑ PAS celui-là

Ouvrez-le dans un éditeur de texte et cherchez le bloc Certificats. Vous y verrez ceci — la valeur de MotDePasse est celle à recopier : 

"Certificats": {
  "Signature":   "/app/certificats/signature.pfx",
  "Chiffrement": "/app/certificats/chiffrement.pfx",
  "MotDePasse":  "<— C'EST CETTE VALEUR>"
}

Les deux chemins sont déjà bons, n'y touchez pas : ce sont ceux du conteneur, expliqués à la section 6.

3. Générer les deux certificats

Dans Git Bash. Placez-vous d'abord dans le dossier prévu : 

cd /c/Users/daryu/source/repos/SchoolWebApp/SchoolWebApp.IdentityServer/certificats

Dans les quatre commandes qui suivent, remplacez MOT_DE_PASSE par la valeur lue à l'étape 2 — celle de appsettings.Production.json. Elle apparaît deux fois, à la fin des commandes 3.1 et 3.2.

Elle doit être identique aux deux endroits. Une lettre de différence, et l'un des deux certificats sera illisible par le serveur — sans que rien ne vous le signale au moment de la création.

Le double slash de //CN= n'est pas une coquille. Git Bash tourne sur MSYS, qui prend tout argument commençant par / pour un chemin Unix et le « traduit » en chemin Windows : /CN=Mimia… devient C:/Program Files/Git/CN=Mimia…, qu'OpenSSL refuse avec le message « subject name is expected to be in the format /type0=value0… ». Le second slash lui dit de ne pas y toucher, et il n'en garde qu'un.

Sous Linux ou macOS, un seul slash suffirait. Deux fonctionnent partout : autant n'avoir qu'une version à retenir.

3.1 — Le certificat de signature

openssl req -x509 -newkey rsa:2048 -sha256 -days 3650 -nodes \
  -keyout signature.key -out signature.crt \
  -subj "//CN=Mimia Identity Signing"

openssl pkcs12 -export -out signature.pfx \
  -inkey signature.key -in signature.crt \
  -passout pass:MOT_DE_PASSE

3.2 — Le certificat de chiffrement

openssl req -x509 -newkey rsa:2048 -sha256 -days 3650 -nodes \
  -keyout chiffrement.key -out chiffrement.crt \
  -subj "//CN=Mimia Identity Encryption"

openssl pkcs12 -export -out chiffrement.pfx \
  -inkey chiffrement.key -in chiffrement.crt \
  -passout pass:MOT_DE_PASSE

3.3 — Effacer les fichiers intermédiaires

Les .key et .crt ont servi à fabriquer les .pfx, qui contiennent désormais tout. Les laisser traîner, c'est laisser la clé privée en clair à côté du coffre. 

rm signature.key signature.crt chiffrement.key chiffrement.crt
ls -l *.pfx

La dernière commande doit afficher deux fichiers : signature.pfx et chiffrement.pfx.

Ce que veulent dire ces options

OptionSignification
-x509Un certificat autonome, pas une demande à envoyer à une autorité.
rsa:2048La taille de la clé. 2048 bits est le standard courant.
-days 3650Dix ans de validité. Voir la section 7.
-nodesPas de mot de passe sur le fichier intermédiaire ; c'est le .pfx final qui en porte un.
-subj "//CN=…"Le nom inscrit dans le certificat. Purement descriptif ici : il n'est vérifié par personne. Le double slash est expliqué plus haut.

4. Vérifier que les fichiers sont corrects

Avant de les transférer, contrôlez-les. Toujours dans Git Bash :

openssl pkcs12 -in signature.pfx -nokeys -passin pass:MOT_DE_PASSE | \
  openssl x509 -noout -subject -enddate

Même chose pour l'autre, en remplaçant signature.pfx par chiffrement.pfx. Faites-le pour les deux : c'est précisément ce contrôle qui révèle une faute de frappe dans le mot de passe, avant qu'elle ne se transforme en serveur qui refuse de démarrer.

Vous devez voir quelque chose comme :

subject=CN = Mimia Identity Signing
notAfter=Aug  9 12:34:56 2036 GMT

Si vous voyez « Mac verify error: invalid password? », le mot de passe utilisé pour créer le fichier n'est pas celui que vous venez de donner. Recommencez la génération : un .pfx dont on a perdu le mot de passe ne se répare pas.

5. Transférer sur le serveur

Les deux fichiers doivent se trouver, sur le VPS, dans le dossier SchoolWebApp.IdentityServer/certificats/ du projet — au même endroit que sur votre machine. 

scp signature.pfx chiffrement.pfx \
  utilisateur@votre-serveur:/chemin/vers/SchoolWebApp/SchoolWebApp.IdentityServer/certificats/

Remplacez utilisateur@votre-serveur et le chemin par les vôtres. Si vous déployez autrement (FTP, panneau d'hébergement, glisser-déposer), peu importe la méthode : seul compte l'emplacement final.

6. Ce qui est déjà configuré

Vous n'avez rien à modifier dans les fichiers ci-dessous : ils sont déjà en place. Cette section existe pour que vous compreniez le montage si vous devez le refaire ou le déplacer un jour.

Le montage — docker-compose.yml

identity:
  volumes:
    - ./SchoolWebApp.IdentityServer/certificats:/app/certificats:ro

Le dossier du serveur est rendu visible dans le conteneur à l'emplacement /app/certificats. Le :ro signifie « lecture seule » : le programme peut les lire, pas les remplacer.

Le renseignement — appsettings.Production.json

"Certificats": {
  "Signature":   "/app/certificats/signature.pfx",
  "Chiffrement": "/app/certificats/chiffrement.pfx",
  "MotDePasse":  "…"
}

Les chemins sont ceux vus depuis l'intérieur du conteneur, pas ceux de votre disque. C'est la ligne volumes ci-dessus qui fait le pont entre les deux. Si vous changez l'une, changez l'autre.

Vérifier que ça marche

Après déploiement, regardez le démarrage du serveur d'identité :

docker compose logs identity | head -40

Si les certificats sont trouvés, le serveur démarre normalement, sans rien dire de particulier. S'ils manquent, il refuse de démarrer et affiche un message qui nomme le fichier introuvable — c'est volontaire : un serveur qui démarrerait quand même donnerait l'illusion que tout va bien, et déconnecterait tout le monde au déploiement suivant.

7. Dans dix ans — le renouvellement

Les certificats expirent le jour indiqué par la commande de la section 4 (notAfter). Notez cette date quelque part : un certificat de signature expiré arrête net l'authentification, plus personne ne peut se connecter.

Pour renouveler : refaites simplement les sections 3, 4 et 5, avec le même mot de passe. Le remplacement déconnecte tous les parents une fois — comme un déploiement ordinaire sans certificats.

8. Les cinq choses à ne pas faire

  1. Ne les mettez jamais sur GitHub. L'extension .pfx est déjà exclue par le .gitignore du projet ; ne l'en retirez pas.
  2. Ne les copiez pas dans l'image Docker. Ils sont montés, pas embarqués : une image qui les contient les expose à quiconque peut la lire.
  3. Ne les régénérez pas sans raison. Chaque remplacement déconnecte l'ensemble des parents.
  4. Ne perdez pas le mot de passe. Sans lui, les fichiers sont inutilisables et il faut tout refaire.
  5. Gardez une sauvegarde des deux .pfx et du mot de passe, ailleurs que sur le serveur — dans votre gestionnaire de mots de passe, par exemple.

9. En cas de problème

SymptômeCause probableQuoi faire
À la génération : « subject name is expected to be in the format /type0=value0… » suivi d'un chemin du genre C:/Program Files/Git/CN=… Un seul slash devant CN=. Git Bash l'a pris pour un chemin. Mettez-en deux : -subj "//CN=…". Voir l'encadré de la section 3.
À la génération : « Could not open file … signature.crt: No such file or directory » La commande précédente a échoué, le .crt n'a jamais été créé. Remontez dans le terminal pour lire la vraie erreur, corrigez-la, et reprenez la section 3 depuis le début.
Le serveur d'identité refuse de démarrer, message « Certificat de … introuvable » Le fichier n'est pas au bon endroit sur le serveur, ou le dossier n'est pas monté. Vérifiez avec docker compose exec identity ls -l /app/certificats.
Erreur au démarrage mentionnant un mot de passe Le mot de passe du .pfx et celui de la configuration diffèrent. Regénérez les .pfx avec le mot de passe lu dans appsettings.Production.json.
Plus personne ne peut se connecter, du jour au lendemain Certificats expirés. Section 7.
Tout le monde est déconnecté à chaque déploiement Les certificats ne sont pas pris en compte. Vérifiez que l'environnement est bien Production et relisez la section 6.
